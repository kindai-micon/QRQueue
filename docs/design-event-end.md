# 受付終了とイベント運用終了の区別(設計案)

- 対応Issue: #74
- ステータス: **提案(運用側との合意が必要)**

## 1. 背景と目的

現在のイベント状態は `Preparing(受付前) / Open(受付中) / Closed(受付終了)` の3状態のみで、
「新規参加の受付を止める」ことと「イベント運用そのものを終了する」ことが区別できない。
issue #74 の課題(受付終了時に待機グループが残る場合の取り扱いが未定義)を受けて、
2つの操作を分離した状態モデルと各状態での振る舞いを定義する。

## 2. 状態モデル(提案)

```
Preparing ──受付開始──▶ Open ──受付終了──▶ QueueClosed ──運用終了──▶ Finished
                          │                     │
                     (任意で受付再開)      (任意で受付再開)
```

| 状態 | 意味 | 新規受付(Join/GroupJoin) | 呼び出し(Next/Again) | チェックイン |
|---|---|---|---|---|
| Preparing | 準備中 | ✗ | ✗ | ✗ |
| Open | 受付中・運用中 | ✓ | ✓ | ✓ |
| QueueClosed | **受付終了**・運用は継続 | ✗ | ✓ | ✓ |
| Finished | **運用終了** | ✗ | ✗ | ✗ |

- 既存の `Closed` は `QueueClosed` に読み替える。`Finished` を新設する。
- **受付終了(QueueClosed)**: 新規の参加登録だけを止める。すでに待機しているグループは、
  従来どおり呼び出し・チェックイン・ゲーム参加を継続できる。
- **運用終了(Finished)**: すべての参加者受付業務を終える。呼び出し・チェックインはできなくなる。

## 3. 各状態への遷移時の取り扱い

### 3.1 受付終了(QueueClosed)に遷移したとき

- 参加登録画面(`/entry/{id}`)は「受付は終了しました」を表示する。
- 待機キュー(Waiting / Calling / Interrupted / Draft)は**そのまま維持**される。
- 呼び出し待ちの Draft グループ(受付確定前)は、そのまま受付確定(Waitingへ)できる
  (#66 の受付フローで確定操作は引き続き可能)。
- 参加者の電子券・Push通知は引き続き機能する。

### 3.2 運用終了(Finished)に遷移したとき

遷移時に、残存する各状態のグループを次のように扱う(**案**。運用側と要合意):

| 残存状態 | 運用終了時の扱い |
|---|---|
| Draft(受付確定前) | Cancelled(受付確定されていないため無効) |
| Waiting(呼び出し待ち) | 参加者による取消ではなく**運用終了による未参加**として `Cancelled` |
| Calling(呼び出し中・未チェックイン) | 同上(`Cancelled`) |
| Interrupted(優先待機) | 同上(`Cancelled`) |
| Matching(マッチングプール) | `Cancelled` |
| Completed(チェックイン済み) | **変更しない**(受付は完了している) |

- 参加者画面: 「イベントの運用は終了しました」と表示する。
- チケット(電子券)は履歴として閲覧可能だが、操作(再参加・チェックイン等)は不可。
  「使用済み(Used)」(#71)、「取消済み(Cancelled)」、
  「運用終了による未参加」は、状態・履歴の上では区別して残す。

## 4. 権限と確認

| 操作 | 権限(既存ポリシー) | 確認 |
|---|---|---|
| 受付終了 | `EventOpenClose` | 確認ダイアログ(「新規受付のみ終了します。待機中のグループは継続して案内できます」) |
| 運用終了 | `EventOpenClose` | **確認ダイアログに残存グループ数を表示**(「待機中 ○組・呼び出し中 ○組が未参加のまま無効になります」) |
| 受付再開(QueueClosed → Open) | `EventOpenClose` | 確認ダイアログ |
| 運用終了からの復帰 | **不可**。誤操作時は DB 操作ではなく、運用上の再発行フローで対応する |

## 5. 履歴の保持

- 運用終了時に各グループへ付けた状態変更は、グループの `Updated` とイベント単位の
  IssueLog(発行ログ)で追跡可能にする。
- 「運用終了による無効化」の事実を確認できるよう、運用終了時にイベント単位の
  ログ(実施日時・実行者・無効化されたグループ数)を記録することを推奨する。

## 6. 実装への反映(対応issue)

| 項目 | 内容 |
|---|---|
| 状態追加 | `EventStatus` に `QueueClosed` / `Finished` を追加(migration 必要) |
| API | `CallController` に `finish/{eventDisplayId}`(運用終了)を追加。`close` は QueueClosed 相当 |
| 参加者画面 | `/entry/{id}`・電子券画面に Finished 時の案内表示 |
| スタッフ画面 | 呼び出しコンソールに「運用終了」ボタン(残存グループ数つき確認)を追加 |
| 参加者への通知 | 運用終了時に SignalR で `UpdateStatus` を配信 |

## 7. 運用側と合意が必要な事項(オープンな論点)

1. 運用終了時に未参加グループを `Cancelled` とすることへの合意
2. 運用終了の実行権限を持つロールの範囲(現在案: `EventOpenClose` 権限保持者)
3. 受付再開の許可方針(運用上、受付終了後に再開するケースがあるか)
4. Finished 後の電子券の閲覧可否(履歴閲覧を許すか、404 にするか。現在案: 閲覧のみ許可)
